# Release engineering (Phase 3.1)

This document records the **verified** state of the release infrastructure and
the policy that still has to be implemented. It is deliberately explicit about
what has NOT been tested. See `docs/architecture/STATUS.md` for the overall
verdicts.

## Versioning

- Single source of truth: `config/version.env` (`SANORA_VERSION`,
  `SANORA_CODENAME`). `build/scripts/build-package.sh` generates `DEBIAN/control`
  from it; `build/scripts/build-repo.sh` generates the `Release` file from it.
  `build-metadata.json`, `sanora-info`, `/etc/sanora/release`, ISO filename and
  `build-info` all derive from the same values. There is no second place where a
  version is typed. The dev version `0.1.0-dev` is **not** a release version.
  A release requires a Debian-policy-compliant version in a real
  `debian/changelog` (the current package is a `dpkg-deb` staging tree), a git
  tag, a changelog, release notes and a signed tag.

- Proposed scheme (NOT yet ratified): `YYYY.MM.patch` for releases, with
  `+sanoraN` for SANORA rebuilds of the same upstream package version.

## Signed APT repository — verified today

`build/scripts/build-repo.sh` builds a local, GPG-signed APT repository at build
time. Verified behaviour (offline test `tests/test_repo.py` plus CI ISO builds):

- `pool/main/s/sanora-base/sanora-base_<version>_all.deb`.
- `dists/sanora/main/binary-amd64/Packages[.gz]`, `dists/sanora/Release`,
  `Release.gpg` (detached armoured signature), `InRelease` (clear-signed), and
  an armoured public key. `gpg --verify Release.gpg Release` is executed; the
  script aborts the build if verification fails. `Release` carries `Origin`,
  `Label`, `Suite`, `Codename`, `Architectures`, `Components`, `Description` and
  a `Date` derived from `SOURCE_DATE_EPOCH` (never the wall clock). `gzip -n`
  is used. `Release.gpg`/`InRelease` are deterministic for a given key and
  `SOURCE_DATE_EPOCH`.

- `build/scripts/assemble-config.sh` wires it into live-build with the supported
  `config/archives/` mechanism:
  `deb [signed-by=/etc/apt/trusted.gpg.d/sanora.key.chroot.asc] file://… sanora main`
  plus `sanora-base` in `config/package-lists/`. `lb build` installs
  `sanora-base` through APT with dependency resolution.
- The key is removed from the final image by live-build's `chroot_archives`
  remove phase (`*.key.chroot` deletions).
- Installed-system check: `tests/install/qemu_install.py` runs
  `apt-get update` in the installed VM and asserts no `NO_PUBKEY`/`GPG error`,
  and asserts the ephemeral development key is **not** present in
  `/etc/apt/trusted.gpg.d/`. Result is recorded in `install-validation.json`
  under `installed.checks.apt_gpg_verification` and
  `ephemeral_dev_key_not_trusted_in_installed_system`. Read the CI verdict
  before claiming a PASS.

## Offline-managed release signing key — NOT implemented

The current key is an **ephemeral development key**, generated by
`SANORA_REPO_AUTO_KEY=1` into `.sanora-dev-gnupg` (Git-ignored). It is stable
across the two same-commit builds (so it does not cause a reproducibility
difference). It is **not** an offline-managed release key. Rotation, expiry,
revocation and hardware-token storage are not implemented. A public release
must NOT use this key.

## Key distribution and rotation policy (design, not yet implemented)

1. Generate one long-lived release key (e.g. RSA-4096 or Ed25519) on an
   air-gapped machine. Store the private key on a hardware token; never in CI,
   never in this repository. Publish only the armoured public key with a
   SHA-256 fingerprint and an out-of-band verification path (HTTPS page +
   signed statement). Distributors pin it with `signed-by=` in a `.sources`
   file, never in the global `/etc/apt/trusted.gpg.d/` trust store. Document the
   fingerprint in `THIRD_PARTY.md`. Rotate on a fixed schedule (e.g. 24 months
   with 3-month overlap where both keys are trusted. Key revocation must be
   published as a signed revocation certificate. Compromise handling: revoke,
   re-sign all `Release` files, publish an advisory. ADR-0012 owns this design.

## Release process (current verified part)

1. `./build.sh --check` (offline validation).
2. ISO build via `iso.yml` (two same-commit builds, boot tests, diffoscope).
3. Install validation via `install.yml` (plain + LUKS2). CI evidence: check runs
   and artifacts. Nothing is published from these development workflows.

**NOT implemented:** signed git tags, release notes, published HTTPS mirror,
`Sources`/`Packages` diff, `aptly`/`reprepro` or equivalent, SBOM, SLSA
attestation, package upload workflow, mirror sync, end-of-life schedule. No
public release exists. No release signing key exists. No claim of release
readiness is made.

## Evidence locations

- `out/build-metadata.json` / `out/reproducibility.json` (ISO jobs).
- `build/work/repo-metadata.json` (key fingerprint, `signature_verified`).
- `out/install-*/install-validation.json` (APT verification in the installed VM).
- GitHub Actions check runs `SANORA build diagnostics`, `SANORA installation
  diagnostics`, `SANORA ISO evidence inspection`.
